Your support agent answers every ticket like it's the first ticket it has ever seen. The customer explained their problem twice already (once on email, once on chat), another customer had the exact same defect last month and got it fixed, and the warranty policy that settles the whole thing is sitting in a PDF nobody retrieves. All the context exists. None of it is in the room when the answer gets written.

This post is the fix, as a pipeline you can copy. We build a support memory layer on xysq with exactly two vaults: a **product brain** (specs, policies: what the company publishes) and a **customer brain** (every message from every customer, all channels, one vault, with PII masked before anything is stored). Two things happen by the end that nobody typed: the system writes its own known-issues doc from repeat defect reports, and it does so without a single real name in it. It's maybe 60 lines of setup code, and everything below ran live against our production API: 12 out of 12 checks, including "zero real identities anywhere".

## The shape: two vaults, three pulls

The mental model first. A good support answer needs three kinds of context, and I think of them as directions:

1. **Vertical context**: everything about *this customer*. Their history, their orders, what they already tried.
2. **Product context**: everything about *the thing itself*. Specs and policies, the official record.
3. **Horizontal context**: *this product across all customers*. Has anyone else hit this? How was it resolved?

Most support stacks have the first one at best (a CRM page the agent skims). The third one is where the leverage is: the official record never says "the March batch flickers", because nobody knew when it shipped. The customers know. Horizontal context is how a support system learns things the company hasn't written down yet.

The architecture that serves all three is small:

- One **project** ("support") that owns a shared tag vocabulary.
- One **product-kb vault**: specs, return policy, warranty policy, billing FAQ. Only official material.
- One **customers vault**: every customer message from every channel, created with `pii_scrub=True`. Not a vault per customer; one vault, with metadata doing the isolation and masking doing the hygiene.

That last point is the part people get wrong. You do not need a thousand vaults for a thousand customers. You need one vault, one declared metadata key, and a mask at the door.

## Tags, metadata, masking (60-second version)

Three primitives, three different jobs:

- **Tags** are a curated vocabulary you control: `defect`, `billing`, `resolved`, `policy`. A tag filter is *hard inclusion*: pull only what carries the tag. Tags live at the project level, so every vault and every agent in the project shares one vocabulary. Unknown tags are never auto-created anywhere: a pull that filters by an unknown tag fails loudly with a 400, and `tags.apply` skips unknown names and echoes them back in the result's `unknown` field.
- **Metadata keys** are identity facets: `customer_id`, `product`. A metadata filter is *match-or-absent*, applied at the finest granularity the engine tracks: a piece of derived knowledge inherits the values of every source that contributed to it, so knowledge derived only from bob's tickets never appears under alice's filter, knowledge derived from both appears under both, and keyless material (policies, specs) appears under everyone's. One sentence to remember: **exclusive content never crosses; shared knowledge serves every side that earned it.**
- **PII masking** cleans content at ingestion, before the first write. Structured identifiers (emails, phones, cards, IPs, IBANs) and any `known_pii` strings you pass become `<redacted>`; names and prose identity get rewritten to neutral voice ("the customer"). If content can't be cleaned, the push is rejected and nothing is stored. Identity then lives where it belongs: in the metadata stamp, not the text.

Rule of thumb: metadata for *who it belongs to*, tags for *what kind of thing it is*, masking so the text itself stops carrying identity at all.

## Step 1: project, vaults, keys

Two prerequisites, both one-time: `pip install git+https://github.com/xysq-ai/sdk_python_xysq.git`, and in the dashboard (app.xysq.ai, under Agents) create a project called "support", copy its id, and mint an agent API key with an **admin grant** on that project (creating vaults and curating tags are project-admin acts; a read or write grant will 403 on the very first call).

```python
from xysq import Xysq

PROJECT_ID = "1f2a..."  # from the dashboard
client = Xysq(api_key="xysq_agent_...")

product_kb = client.vaults.create("product-kb", project_id=PROJECT_ID)
customers  = client.vaults.create("customers",  project_id=PROJECT_ID,
                                  pii_scrub=True)
```

Two things matter here. Creating the vaults inside the project is what lets them resolve the project's shared tag vocabulary later. And `pii_scrub=True` on the customers vault means every push into it gets masked before storage; the product brain holds public material and doesn't need it. (Needs SDK ≥ 3.6.0.)

## Step 2: declare the metadata keys

Declaring a key is what turns a metadata field into a filter. Undeclared fields are stored but not filterable.

```python
client.vaults.declare_meta_key(customers.vault_id, "customer_id")
client.vaults.declare_meta_key(customers.vault_id, "product")
client.vaults.declare_meta_key(product_kb.vault_id, "product")
```

(If you declare a key after you've already ingested, a backfill extracts it from existing sources in the background. Order doesn't trap you.)

## Step 3: curate the tag vocabulary

```python
for name in ["policy", "defect", "billing", "resolved"]:
    client.tags.create(PROJECT_ID, name)
```

Four tags is a fine start. Resist the urge to mint fifty; the vocabulary is a filter surface, not a folksonomy (free-for-all tagging where anyone mints anything). Deleting a tag archives it (nothing gets untagged, and you can restore it), so curating is cheap. Notice what's *not* here: no `known-issue` tag. We don't know the issues yet. That's the point.

## Step 4: ingest the product brain

Only what the company publishes. Our full fixture is three docs; here they all are, so your run reproduces ours. Note the return policy gets pushed with *no* product metadata: match-or-absent means it stays reachable from every product-scoped pull.

```python
kb_docs = [
    ("Return policy",
     "Returns are accepted within 30 days of delivery. Defective units are "
     "replaced free of charge at any time during the 12-month warranty; the "
     "customer does not pay return shipping for a defect.",
     None, ["policy"]),
    ("Widget Pro spec",
     "Widget Pro is the 27-inch model with the M3 display controller, "
     "firmware line 4.x. Sold since January 2026.",
     "widget-pro", []),
    ("Billing FAQ",
     "Invoices are issued on the 1st. Duplicate charges are refunded within "
     "3 business days once reported.",
     None, ["policy", "billing"]),
]
for title, content, product, tags in kb_docs:
    r = client.vaults.push(product_kb.vault_id, content, title=title,
                           metadata={"product": product} if product else None)
    if tags:
        client.tags.apply(product_kb.vault_id, r.id, add=tags)
```

There is no known-issues doc in that list, and there never will be. Watch what happens instead.

## Step 5: ingest the customer brain, through the mask

Every message, every channel, one vault, stamped with who and what. The helpdesk knows each customer's real identifiers, so it passes them as `known_pii`; they're used for masking and never stored. Our fixture is four messages from three customers:

```python
tickets = [
    ("alice", "widget-pro",
     "Alice Chen (alice.c@example.com) reported: my Widget Pro screen "
     "flickers every few minutes at 120Hz. Purchased in March. Order #A-1042.",
     ["Alice Chen", "alice.c@example.com", "#A-1042"], ["defect"]),
    ("alice", "widget-pro",
     "Alice Chen followed up on chat: the flicker on her Widget Pro is worse "
     "after the room warms up. She already tried a different cable.",
     ["Alice Chen"], ["defect"]),
    ("bob", "widget-pro",
     "Bob Fischer (bob.f@example.com) reported flicker on his March-batch "
     "Widget Pro. Resolution: support had him update to firmware 4.2; "
     "flicker persisted, so a warranty replacement was shipped. He confirmed "
     "the replacement unit is stable.",
     ["Bob Fischer", "bob.f@example.com"], ["defect", "resolved"]),
    ("carol", "widget-mini",
     "Carol Dane (carol.d@example.com) was charged twice for her Widget Mini "
     "order #C-2210. Refund of the duplicate charge requested.",
     ["Carol Dane", "carol.d@example.com", "#C-2210"], ["billing"]),
]
for customer, product, content, known, tags in tickets:
    r = client.vaults.push(customers.vault_id, content,
        metadata={"customer_id": customer, "product": product},
        known_pii=known)
    client.tags.apply(customers.vault_id, r.id, add=tags)
```

Here's what the vault actually stored for alice's first ticket, read straight back from the database in our run:

```
The customer reported: my Widget Pro screen flickers every few minutes
at 120Hz. Purchased in March. Order <redacted>.
```

No name, no email, no order number, full meaning. We asserted it hard: across every stored row in the customers vault, zero of the eight real identifiers from the fixture survived. The symptom, the batch, the firmware level, the resolution: all intact. Identity lives in the `customer_id` stamp, where filters can use it and text can't leak it.

In production this loop is a webhook from your helpdesk, chat, and email pipeline, not hand-written fixtures. The point is the shape: content + identity metadata + `known_pii` + one or two curated tags per message. Give indexing a minute before you pull (our run waited 60 seconds).

## The three pulls

A ticket comes in: alice, flicker, Widget Pro. Your agent (human or AI) makes three pulls.

**Vertical: this customer's history.**

```python
history = client.vaults.pull(
    customers.vault_id,
    query="screen flicker history",
    filters={"meta": {"customer_id": "alice"}},
)
for item in history:
    print(item.title, "::", item.content[:80])
```

Pull returns a list of items (each has `title`, `content`, `source`, `score`). In our live run this returned alice's two tickets, the extracted symptom facts, and (this is the part we didn't script) a distilled wiki page titled *"Widget Pro Flicker Issue"* that the engine had consolidated from the repeat reports. The page appears in alice's pull because her tickets helped derive it; bob's pull gets the same page for the same reason. What alice's pull does NOT contain: carol's billing issue (different customer, excluded by her stamp), and any real name at all: the whole result set is "the customer" and `<redacted>`, because that's all the vault ever stored.

**Product: the official record.**

```python
policy = client.vaults.pull(
    product_kb.vault_id,
    query="flicker warranty replacement policy",
    filters={"meta": {"product": "widget-pro"}},
)
```

Returns the Widget Pro spec and the warranty policy (which, remember, has no product stamp and survives the filter by design). Note what it does *not* return: anything about flicker being a known problem. The official record doesn't know yet.

**Horizontal: this product across all customers.**

```python
similar = client.vaults.pull(
    customers.vault_id,
    query="how was the flicker resolved",
    filters={"meta": {"product": "widget-pro"}, "tags": ["defect"]},
)
```

Metadata and tags compose in one call: only Widget Pro sources, only the ones tagged `defect`. Our run's top item, verbatim:

```
The customer reported flicker on the March-batch Widget Pro. Resolution:
support had the customer update to firmware 4.2; flicker persisted, so a
warranty replacement was shipped.
```

That's the prior fix, fully anonymous, sitting next to the emergent *"Widget Pro Flicker Issue"* page. Nobody wrote a known-issues doc. The system wrote it, from three tickets, versioned it in the vault's wiki layer, and because masking happened at the door, the page physically cannot name anyone. Carol's billing issue on a different product was correctly invisible.

That is the "self-realising" moment, and it's not magic: repeat facts across sources are exactly what a distillation layer consolidates. Two customers reporting the same flicker on the same batch *is* the known issue; the wiki page is just that pattern made retrievable, and safe to hand to any customer-facing agent as-is.

The agent now knows this is a repeat March-batch defect, knows the fix that actually worked, and knows the policy that authorizes it. The reply writes itself: "this is a known issue with March units; firmware 4.2 sometimes helps, but you qualify for a free warranty replacement either way."

## The learning loop

Close the loop by pushing the resolution back:

```python
r = client.vaults.push(
    customers.vault_id,
    "Confirmed March-batch defect, same as the earlier case. Firmware 4.2 "
    "did not resolve it; warranty replacement shipped per policy. Customer "
    "confirmed fixed.",
    metadata={"customer_id": "alice", "product": "widget-pro"},
)
client.tags.apply(customers.vault_id, r.id, add=["defect", "resolved"])
```

Now the emergent known-issue page has *two* confirmed resolutions feeding it, and the next agent's horizontal pull starts from a stronger page. Ticket by ticket, the "March batch flickers" pattern goes from a vibe spread across tickets to a first-class piece of context. When the pattern is loud enough, that page is also your signal to engineering: the support system noticed the defective batch before anyone filed it.

This works identically whether the thing making the pulls is a human agent's dashboard or an AI agent drafting replies. Same three pulls, same filters. Either way the answer comes from what your customers and docs actually said, not from what a model half-remembers.

## Honest constraints (read before you build)

- **Filters are single-vault per pull.** You can't join the customer brain and the product brain in one call; you make three pulls (they're independent, run them concurrently).
- **Shared knowledge is visible from every contributing side.** That's the design, not a leak: a finding derived from alice's and bob's tickets serves both of their filtered pulls. With masking on, that shared knowledge carries no identities anyway. Exclusive content never crosses.
- **A tag filter's scope is capped at 1,000 sources**, checked on the tag closure alone. If `defect` alone outgrows that, split the vocabulary: `defect-display`, `defect-battery`.
- **Masking has exact edges.** The deterministic guarantee covers emails, phones (10+ digits), Luhn-valid cards, IPv4/IPv6, IBANs, and every `known_pii` string; unknown prose names are handled by the model pass, best-effort. Unscrubable content is rejected with a 422 and nothing is stored. Because the rewrite isn't byte-deterministic, re-pushing identical raw content may not dedupe on a masked vault. Full details in the [PII scrubbing docs](https://docs.xysq.ai/sdk/pii-scrub).
- **Tags are applied after push** (push returns the source id, then `tags.apply`). Two calls today.

## Build it

The whole pipeline is two vaults (one masked), three declared keys, four tags, and three pulls. Our reference run: 7 documents ingested through the mask, ~60 seconds of indexing, 12 out of 12 checks passed against production, including zero real identities in any stored row or any served pull.
